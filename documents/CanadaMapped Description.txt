Canada Mapped is a full-stack web application at canadamapped.ca that lets users find Statistics Canada data tables using natural language queries and visualizes the results as a choropleth map of Canadian provinces. A user types something like "average household spending on food by province" and the app finds the most relevant StatCan table, fetches the latest data for each province, and renders it on an interactive map.

ARCHITECTURE

The project has three main layers. The frontend is built with React and Vite and deployed on Vercel. It handles query input, province map rendering, and dimension selection such as choosing age group or industry breakdowns. The backend is a Node.js and Express server deployed on Render. It exposes a search endpoint that takes a natural language query and returns the best matching StatCan cube with metadata and province data coordinates, plus a data endpoint that fetches the latest values per province given a cube ID and selected dimension members. The data pipeline is a set of offline scripts in the canada-data-pipeline directory that call the StatCan API, collect and filter cube metadata, and generate pre-computed embeddings. It runs once to build the search index and does not run at request time.

DATA COLLECTION AND INDEXING

The StatCan WDS REST API is used to fetch all roughly 8000 StatCan tables, filter down to roughly 3600 tables that contain data for all 10 Canadian provinces, and extract rich metadata per table including title in English and French, date range, update frequency, archive status, subject codes, survey codes, dimensions and their member names, and footnotes. This metadata is saved to cubesMetadata.json and used both for building the embedding index and for enriching search results at request time.

SEMANTIC SEARCH

At query time the backend embeds the user's query using a sentence-transformer model and computes cosine similarity against pre-computed cube embeddings. All embeddings are normalized unit vectors so cosine similarity reduces to a dot product. The embedding inference runs in-process using Xenova Transformers.js, which is a JavaScript port of the HuggingFace Transformers library. The primary embedding model is all-MiniLM-L12-v2 which produces 384-dimensional vectors. Other models evaluated include all-MiniLM-L6-v2, paraphrase-MiniLM-L3-v2, all-mpnet-base-v2, and bge-small-en-v1.5.

Two approaches to document text for the cube embeddings have been explored. The baseline approach embeds only the table title plus start and end dates, which averages about 17 tokens per document and achieved 32.3 percent top-1 accuracy. The enriched approach embeds the title plus dates plus IDF-filtered dimension names and member names, averaging about 87 tokens per document. IDF document frequency thresholding at 5 percent filters out generic cross-cutting terms like NAICS industries, Sex, and Age group that appear in too many cubes to be discriminative, while keeping subject-specific vocabulary. In practice the enriched approach hurt accuracy, dropping to roughly 22 to 23 percent, because member names in adjacent wrong cubes created false-positive keyword matches in embedding space.

An asymmetric retrieval model, multi-qa-MiniLM-L6-cos-v1, has also been investigated. This model was trained on short query and longer passage pairs, so it handles the mismatch between 10-word queries and 87-word enriched cube text without the mean-pooling distortion that symmetric models suffer from at different query and document lengths. A configurable members-per-dim flag controls how many member names per dimension are included in the document text, allowing experiments with 0 (dimension names only), 2, or 8 members per dimension.

RE-RANKING PIPELINE

After the initial cosine similarity ranking, three multiplicative score adjustments are applied. First, an MLP classifier predicts which of 30 subject categories the query belongs to, and cubes whose mapped category matches the prediction get their score multiplied by 1.15. Second, per-category top-distinctive keywords built offline via TF-IDF over table titles are matched against the raw query text, with each matching keyword multiplying the score by 1.05, compounding up to 5 matches for a maximum boost of about 28 percent. Third, tables marked as non-current by StatCan get their score multiplied by 0.85 before the other boosts are applied, deprioritizing outdated tables without excluding them.

MLP QUERY CLASSIFIER

The MLP classifier is trained using TensorFlow.js. Its architecture takes a 384-dimensional query embedding as input, passes it through hidden layers, and outputs a 30-class softmax over StatCan subject categories. Training data consists of real user-style queries collected via the Serper Google Search API, then labeled to StatCan categories via a hand-built subjectCodeToCategory.json file that maps StatCan's 400-plus subject codes to 30 categories. The classifier weights are saved as JSON and loaded at runtime without requiring a native TensorFlow dependency. A separate all-MiniLM-L12-v2 model instance always produces the query embedding for the MLP regardless of which retrieval model is active, because the MLP was trained on those specific vectors.

BENCHMARKING

Ground truth is collected by running each query through the Serper Google Search API and extracting the StatCan table URLs from the results. Each StatCan table URL contains a pid parameter encoding a 10-digit number where the first 8 digits identify the cube. A benchmark script queries the live search endpoint for each ground-truth query and compares the returned cube ID against the expected cube IDs.

Queries are bucketed into three groups. No-link queries have no Google result and are excluded. Unwinnable queries have a Google result pointing to a cube not in the search index, so the system can never return the right answer, and they are excluded from the accuracy denominator. Winnable queries, roughly 1323 of the 2295 total, form the accuracy denominator. Metrics tracked include top-1, top-3, and top-5 accuracy, plus a breakdown of misses into same-category (right subject area, wrong specific table) versus different-category (completely wrong direction) misses. A lightweight test server separate from the production server skips live StatCan API calls during benchmarking and returns the full top-K candidate list instead of just the single winner, enabling top-3 and top-5 measurement and making benchmark runs order-of-magnitude faster.
