Project: A client-heavy semantic search + RAG (retrieval-augmented generation)
prototype for a React portfolio site. Frontend currently generates queries and
uses a mocked backend API (api/chat.js) while in-browser query-embedding logic and
Openroute API integration are being implemented.

Overview: User text is embedded (planned in-browser), nearest-neighbor retrieval
returns top documents/snippets from a precomputed vector index, and a backend
composes contextual prompts for an LLM to produce final answers. Mock API stands
in for the retrieval/LLM integration during development.

Tech Stack:

 - Frontend: React (Vite), client-side JS for embedding
 - Backend: Node serverless/API route (api/chat.js) placeholder
 - Embeddings: client-side model (WebAssembly/ONNX or remote embeddings)
 - Vector index options: FAISS, Annoy, HNSWlib, or managed (Pinecone, Qdrant, 
Milvus, Weaviate, PGVector)
 - LLM: hosted API (Openroute mentioned) or OpenAI/compatible model
 - Infra: CDN, object storage (S3), secrets manager, serverless hosting 
(Vercel/Netlify) or container hosts

Architecture:

 - In-browser: tokenize & embed query → send vector (or raw query) to backend
 - Backend: vector DB lookup (ANN) → retrieve top-k chunks with metadata → rerank 
/ filter (temporal, source) → assemble prompt/context → call LLM → return answer +
 provenance
 - Indexing pipeline: document chunking, embedding, metadata store, periodic 
reindexing

Important technical decisions:

 - Embedding location: browser (privacy & latency) vs server (consistency, smaller
 client binary)
 - Index type: ANN (HNSW/IVF+PQ) for low-latency at scale
 - Hybrid retrieval: lexical (BM25) + dense vectors to improve precision
 - Context window management and chunk-size tradeoffs to avoid prompt overrun
 - Provenance: attach source ids + offsets for traceability

Challenges:

 - Client resource limits (CPU, memory) and model size for in-browser embeddings
 - Secure storage/use of API keys in client vs serverless
 - Index freshness and incremental updates for mutable content
 - Handling near-duplicate chunks and long documents (chunking + overlap)
 - Cost/latency of LLM calls; batching and caching top-k responses
 - Evaluation: building relevance labels and offline metrics

Performance / Scaling considerations:

 - Index sharding, replication, and ANN tuning (ef/search_k, M, PQ bits)
 - Quantization to reduce storage (int8/PQ) vs reduced accuracy
 - Caching hot queries and top-k embeddings; TTLs for dynamic content
 - P50/P95 latency targets (vector lookup + LLM call pipeline) and throughput 
planning (QPS)
 - Monitoring: recall@k, MRR/NDCG, freshness, error rates, cost per query


Outcomes:

 - Provides semantic recall where lexical search misses paraphrases and synonyms
 - Expected measurable goals: higher recall@k and MRR for intent-based queries, 
reduced mean time-to-answer versus keyword search, controlled LLM call volume via 
retrieved-context filtering and reranking
 - Traceability via source-level provenance enables auditing and user-facing 
citations
