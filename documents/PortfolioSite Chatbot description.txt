# Project

Labrador is a client-heavy semantic search and RAG prototype for a React portfolio website. The frontend generates user queries and sends them to a mocked backend API (api/chat.js). In-browser embedding logic and OpenRouter API integration are being developed.

---

## Overview

User queries are embedded (planned in-browser) and used for nearest-neighbor retrieval over a precomputed vector index. The backend composes contextual prompts for an LLM to generate final answers. During development, a mock API simulates retrieval and LLM orchestration.

---

## Tech Stack

Frontend uses React (Vite) with client-side JavaScript for embedding.

The backend is a Node.js serverless API route (api/chat.js placeholder).

Embeddings are generated using a client-side model (WebAssembly/ONNX or remote embedding API).

The LLM layer uses OpenAI mini 5.4.

Infrastructure is deployed on Vercel using serverless hosting.

---

## Architecture

In-browser processing tokenizes and embeds queries before sending vectors (or raw queries) to the backend.

The backend performs vector database lookup using approximate nearest neighbor (ANN) search, retrieves top-k chunks, filters results, and assembles a prompt context for the LLM.

The indexing pipeline includes document chunking, embedding generation, metadata storage, and periodic reindexing.

---

## Important Technical Decisions

Embedding can be performed in-browser for privacy and latency or on the server for consistency and reduced client complexity.

The system uses ANN indexing (HNSW or IVF+PQ) for scalable low-latency retrieval.

A hybrid retrieval approach combines lexical search (BM25) with dense vector search to improve precision.

Context window management and chunk sizing are optimized to prevent prompt overflow.

Each retrieval result includes provenance metadata such as source IDs and offsets for traceability.

---

## Challenges

Client-side constraints such as CPU usage, memory limits, and model size impact in-browser embedding performance.

API key security must balance between client exposure and serverless execution.

Index freshness requires strategies for incremental updates as documents change.

Long documents and near-duplicate chunks require careful chunking and overlap tuning.

LLM cost and latency require batching, caching, and strict context filtering.

Evaluation requires building relevance labels and measuring retrieval quality using metrics like recall@k and MRR.

---

## Outcomes

The system improves semantic recall compared to keyword search by capturing paraphrases and intent-based queries.

Expected improvements include higher recall@k, improved MRR, and reduced time-to-answer.

Retrieval provenance enables explainability and supports user-facing citations and auditing.
